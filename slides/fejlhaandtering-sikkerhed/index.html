02 Statuskoder

Statuskoder

Tallet i svaret fortæller klienten, hvad der skete, før den har læst et eneste ord.

Hvad

Tre familier: hvem skal rette fejlen?

En statuskode er et tal på tre cifre, som serveren sender med i hvert svar. Det fortæller klienten, hvordan det gik, før den læser selve indholdet.

2xx

Det lykkedes

  • 200 OK
  • 201 Created
  • 204 No Content

GET /students gav listen

4xx

Klienten bad om noget forkert

  • 400 Bad Request
  • 404 Not Found

PUT /students/999: id'et findes ikke

5xx

Serveren fejlede selv

  • 500 Internal Server Error

students.json er i stykker

Første ciffer er nok: 4xx betyder "ret din request", 5xx betyder "vi har et problem".

Hvorfor

Klienten læser tallet, ikke teksten

Sådan tjekker en frontend svaret 
const response = await fetch(
  "http://localhost:3000/students/999"
);

if (!response.ok) {
  // 4xx eller 5xx: vis en fejl
}

const student = await response.json();
Uden statuskode

200 og et tomt svar. response.ok er true, så frontenden prøver at vise en studerende, der ikke findes.

Med statuskode

404. response.ok er false, så frontenden kan vise "Studerende ikke fundet".

response.ok er true for alle 2xx. Samme tal ses i Thunder Client og i browserens Network-fane.

Hvilke er vigtige

Statuskode-kort for /students

RouteLykkesKan fejle med
GET /students200500
GET /students/:id200404500
POST /students201400500
PUT /students/:id200404400500
DELETE /students/:id204404500204 har ingen body

Seks koder dækker hele jeres API. 500 kan ske overalt, og den håndterer vi ét sted i kapitel 6.

Hvordan · vis det live i Thunder Client

.status() før .json() eller .send()

Før · Express sætter 200 
// POST /students
response.json(newStudent);

// DELETE /students/:id
response.send();
→
Efter · I bestemmer 
// POST /students
response.status(201).json(newStudent);

// DELETE /students/:id
response.status(204).send();

.status() sætter kun tallet. Det er .json() eller .send(), der sender svaret afsted.

03 Fejlhåndtering

Fejlhåndtering

Hvad gør API'et, når en request ikke kan lykkes? Vi starter med 404 ved id'er, der ikke findes.

Hvad

To slags fejl, to slags værktøj

Kan I tjekke for fejlen med et if, før den sker?
Ja

Forventet fejl

Hvem
Klienten bad om noget forkert
Fx
Id'et findes ikke 404
Et felt mangler 400
Værktøj
if + return i routen
if (!student) {
  response.status(404).json({ error: "..." });
  return;
}
Nej

Uventet fejl

Hvem
Serveren fejlede selv
Fx
Datafilen mangler 500
En bug, I ikke har set 500
Værktøj
try/catch + fejl-middleware
try {
  return JSON.parse(data);
} catch (error) {
  throw new Error("Kunne ikke hente studerende");
}

Forventede fejl er 4xx, uventede er 5xx. Uanset hvad: et tydeligt svar, og serveren kører videre.

Hvorfor

Det her får klienten lige nu

PUT /students/999 500 Internal Server Error text/html

    at file:///Users/aisha/students-rest-api/routes/students.js:34:16

  1. Forkert tal500 siger "serverens skyld". Det var klientens id, der var forkert.
  2. HTML, ikke JSONFrontendens response.json() fejler.
  3. Afslører detaljerFilstier, mappenavne og linjenumre fra jeres server.

find() gav undefined, og routen prøvede alligevel at sætte student.name.

Hvordan · guard clause

Tjek. Svar. Stop.

Guard clause: et if øverst i routen, der fanger fejlen, svarer, og stopper routen med return. Så handler resten kun om den lykkelige vej.

students.find(...)
↓
Fandt vi en studerende?
↓
Nej404 + return
routen stopper
Jafortsæt til
response.json()
router.get("/:id", async (request, response) => {
  const students = await loadStudents();
  const student = students.find(
    (student) => student.id === Number(request.params.id)
  );

  if (!student) {
    response.status(404).json({
      error: "Ingen studerende med det id findes."
    });
    return;
  }

  response.json(student);
});

Husk return: response.json() sender svaret, men stopper ikke funktionen.

Hvor

Alle routes med :id, og DELETE er lumsk

404-tjek hører til i

GET /students/:id

PUT /students/:id

DELETE /students/:id

Alle finder én bestemt ressource ud fra id'et. Mønsteret er det samme: find() først, så if (!student).

DELETE /students/999 uden tjek

findIndex() finder ikke noget og giver -1. splice(-1, 1) sletter det sidste element.

Aisha[0] Noah[1] Sofie[-1]

Med filter() slettes intet, men I får stadig 204.

I begge tilfælde får klienten ikke at vide, at der ikke var noget at slette.

04 Validering

Validering

Samme mønster som 404, bare på inputtet. Tjek request.body, før I gemmer noget.

Hvad og hvorfor

API'et gemmer alt, hvad det får

Validering betyder at tjekke, at input er brugbart, før du bruger det. Klienten kan være hvem som helst: jeres frontend, Thunder Client, curl eller et script. Stol aldrig på input.

POST /students 200 OK
// request body
{ "name": "Test" }
data/students.json
[
  { "id": 1, "name": "Aisha", "education": "Datamatiker" },
  { "id": 1758792000000, "name": "Test" }
]

I AMAbotten: POST /answers med kun { "category": "test" } giver en halv svarregel.

Hvordan

Samme guard clause, nu på request.body

router.post("/", async (request, response) => {
  const students = await loadStudents();

  if (!request.body.name || !request.body.education) {
    response.status(400).json({ error: "name og education skal begge udfyldes." });
    return;
  }

  const newStudent = {
    id: Date.now(),
    name: request.body.name,
    education: request.body.education
  };
  students.push(newStudent);
  await saveStudents(students);
  response.status(201).json(newStudent);
});

I PUT står 400-tjekket efter 404-tjekket: findes studerenden ikke, er der intet at validere.

05 try / catch

Fang fejlen,
dér hvor den opstår

Nogle fejl kan I ikke tjekke jer ud af med et if. Dem fanger I med try/catch.

Hvad · helt enkelt først

Prøv det her. Går det galt, så fang det her.

try · prøv det her 
try {
  // kode, der måske fejler
}
catch · hvis det går galt, fang det her 
catch (error) {
  // kører kun, hvis noget i try fejlede
}
// programmet kører videre herfra
Går det godt

Al koden i try kører. catch springes over.

Går det galt

Resten af try springes over, og catch kører i stedet.

error

Selve fejlen. error.message er beskeden.

Uden try/catch ryger fejlen bare videre. Med try/catch bestemmer I selv, hvad der skal ske.

Samme idé i loadStudents()

Hvad kan gå galt i loadStudents()?

try {
  const data = await fs.readFile(
    "./data/students.json", "utf8"
  );
  return JSON.parse(data);
} catch (error) {
  // hvad skal der stå her?
}
Alt går godt readFile ✓→ JSON.parse ✓→ return
Filen mangler readFile ✗→ JSON.parse→ catch (error)
Ugyldig JSON readFile ✓→ JSON.parse ✗→ catch (error)

Fejler en linje i try, springer JavaScript til catch. Et if kan ikke se, om filen er i orden, før I prøver.

Men hvad skal der stå i catch?

Data-modulet kan ikke svare klienten

Fristende, men virker ikke · data/students.js

  try {
    const data = await fs.readFile(
      "./data/students.json", "utf8"
    );
    return JSON.parse(data);
  } catch (error) {
    response.status(500).json({ error: "..." });
  }
}
Terminalen
ReferenceError: response is not defined
response findes kun i routen 
router.get("/", async (request, response) => {

Express giver routen request og response som parametre.

loadStudents() får ingen

Og det skal den heller ikke. Data-modulet handler om filer, ikke om HTTP.

Data-modulet kan ikke svare. Det kan kun sige "det gik galt" til den, der kaldte det. Det gør man med throw.

Nyt · throw new Error()

Kast jeres egen fejl

throwstop her, og send fejlen op til den, der kaldte new Error(opret en fejl "Kunne ikke hente studerende"beskeden, der bliver til error.message );
1 · Funktionen stopper

Linjerne efter throw kører ikke.

2 · Fejlen ryger op

Til den, der kaldte funktionen.

3 · Den kan fanges

Af den, der kaldte, med catch (error). Beskeden står i error.message.

I jeres API er det routen, der kalder loadStudents(). Så det er dér, fejlen lander.

Løsningen · throw i catch

Fang den tekniske fejl, kast en tydelig fejl

06 Middleware

Middleware
& fejl-middleware

Kode, der kører mellem request og response. I har brugt det hele tiden. Nu skriver I jeres egen.

Hvad

Middleware kører mellem request og response

Middleware er en funktion, som Express kører på vejen fra request til route. Fælles arbejde løses ét sted, i stedet for i hver route.

request→ express.json()læser body'en ind i request.body→ cors()sætter CORS-headers (AMAbot)→ studentsRouterjeres routes→ response 
app.use(express.json());   // middleware
app.use(cors());           // middleware
app.use("/students", studentsRouter);

Hver middleware kalder next() for at sende requesten videre til den næste i rækken.

Fejl-middleware

Fire parametre: Express kalder den kun ved fejl

app.use((error, request, response, next) => {
  console.error(error);                                  // hele fejlen, til jer, i terminalen
  response.status(500).json({ error: error.message });   // kort besked, til klienten
});
Fire parametre

error først. Det er sådan, Express kender forskel på den og en almindelig middleware.

Kun ved fejl

Kaldes, når en route eller et modul har kastet en fejl. Ellers springes den over.

Står sidst

Nederst i server.js, efter routerne. Den fanger kun fejl fra det, der står over den.

next skal stå der, selvom I ikke bruger den. Ellers har funktionen kun tre parametre.

Hvad sparer fejl-middlewaren os for?

Begreberne igen

Middleware og de fire begreber

SoC Fælles opgaver ligger uden for routerne Routerne handler kun om students. Body, CORS og fejlsvar klares af middleware.
DRY Skrives én gang, gælder for alle routes app.use(express.json()) én gang. Én fejl-middleware i stedet for try/catch i ti routes.

07 CORS

Tillad kun jeres
egen frontend

Lige nu må enhver hjemmeside kalde AMAbottens API og læse svaret fra en brugers browser. Det lukker vi.

Definition

Hvad er CORS?

Cross-Originpå tværs af origins Resource Sharingdeling af data

CORS er den måde, en server giver en anden origin lov til at læse sine svar i browseren. Det sker med HTTP-headeren Access-Control-Allow-Origin.

1 · Browseren blokerer

Som udgangspunkt må JavaScript kun læse svar fra sin egen origin. Det hedder same-origin policy.

2 · Serveren giver lov

Med en header i svaret. Det er det, cors() sætter.

3 · Kun i browseren

Thunder Client og curl er ikke browsere. De får svar uanset.

To ord at forstå: origin og lov. Dem tager vi ét ad gangen.

Definitionen · origin

Protokol + vært + port

http://protokol 127.0.0.1vært :5500port /index.htmlsti · ikke en del
http://127.0.0.1:5500/about.htmlSammeKun stien er anderledes
http://localhost:5500AndenVærten er anderledes, selvom det er samme computer
http://127.0.0.1:3000AndenPorten er anderledes
https://127.0.0.1:5500AndenProtokollen er anderledes

Browseren sammenligner som tekst. Frontend på 127.0.0.1:5500 og API på localhost:3000 er to origins.

Definitionen · lov, trin for trin

Serveren svarer altid. Browseren bestemmer.

Står jeres origin i Access-Control-Allow-Origin, får JavaScript svaret. Ellers ikke.

Problemet · lov til alle

cors() uden argumenter tillader alle

app.use(cors());
Response-header, uanset hvem der spørger
Access-Control-Allow-Origin: *
Demo · konsollen på http://localhost:5500 
fetch("http://localhost:3000/messages")
  .then((r) => r.json()).then(console.log);

Virker, for * betyder alle origins. Thunder Client virker altid: den er ikke en browser.

Diskutér to og to

Hvad kunne en fremmed hjemmeside gøre med jeres /messages og /answers?

  • Læse alle beskeder: GET /messages
  • Slette dem: DELETE /messages
  • Plante svarregler: POST /answers
  • DELETE og POST med JSON: browseren spørger serveren om lov først. Uden lov bliver de slet ikke sendt.

/students har aldrig fået cors(). Dér blokerer browseren allerede.

Løsningen · lov til én

Tillad kun den origin, I selv bruger

Før · alle 
app.use(cors());

// Access-Control-Allow-Origin: *
→
Efter · kun jeres frontend 
app.use(cors({ origin: "http://127.0.0.1:5500" }));

// Access-Control-Allow-Origin: http://127.0.0.1:5500
Konsollen på http://localhost:5500, efter rettelsen
Access to fetch at 'http://localhost:3000/messages' from origin 'http://localhost:5500' has been blocked by CORS policy:
The 'Access-Control-Allow-Origin' header has a value 'http://127.0.0.1:5500' that is not equal to the supplied origin.

CORS virker kun i browseren. Thunder Client og curl får stadig svar, og /answers er stadig åben for alle.

08 XSS · Cross-Site Scripting

Når tekst
bliver til kode

Et spørgsmål kan indeholde HTML. Lige nu gemmer AMAbotten det, og frontenden kører det.

Definition

Hvad er XSS?

Cross-Sitei en anden brugers browser ScriptingJavaScript, der kører

XSS er, når en brugers tekst bliver kørt som kode på jeres side, i en anden brugers browser. Vi prøver det i tre trin.

1 · Brugeren skriver

Et spørgsmål med HTML-tags i stedet for almindelig tekst.

2 · Serveren gemmer

Uredigeret i messages.json. Nu er det en del af jeres data.

3 · Frontenden viser

Med insertAdjacentHTML(). Browseren kan ikke se forskel på jeres kode og angriberens.

X i stedet for C, så det ikke forveksles med CSS.

Trin 1 · tekst bliver til HTML

<b>hej</b> som spørgsmål

POST /messages · question<b>hej</b>
Som HTML 
list.insertAdjacentHTML(
  "beforeend", `<li>${message.text}</li>`
);
Browseren viserhej

Browseren læser <b> som et tag. Harmløst, men det er hullet.

≠
Som tekst 
const li = document.createElement("li");
li.textContent = message.text;
list.append(li);
Browseren viser<b>hej</b>

Tegnene vises, som de er. Intet bliver til et tag.

Tegnene < og > gør tekst til tags. Kan browseren ikke læse dem som tags, er der intet at køre.

Trin 2 · HTML, der kører kode

Samme hul, nu med onerror

1 · Thunder Client · POST /messages 
{ "question": "<img src=x onerror=\"alert('hacked')\">" }

Billedet x findes ikke, så onerror kører. <script> virker ikke her: browseren kører ikke script-tags fra insertAdjacentHTML().

2 · data/messages.json 
"text": "<img src=x onerror=..."

Gemt præcis, som den kom.

3 · Genindlæs frontenden
Browseren viser⚠ hacked

Beskeden ligger på serveren. Alle, der åbner siden, får alerten. Hver gang.

Trin 3 · koden gør skade

alert() er kun beviset

Samme hul, værre spørgsmål 
<img src=x onerror="
  fetch('http://localhost:3000/messages',
    { method: 'DELETE' })">
Værst i AMAbotten · svaret

/answers er stadig åben for alle. En plantet svarregel rammer alle, der stiller et matchende spørgsmål, og ikke kun den, der oprettede den.

Diskutér to og to

Hvad kan et script gøre, når det kører på jeres side?

  • Læse alt, brugeren kan se på siden
  • Sende requests i brugerens navn: slette alle beskeder
  • Skifte siden ud med en falsk login-formular
  • CORS hjælper ikke. Scriptet kører på jeres frontend, og den origin har I selv givet lov.

"Cross-site": angriberens kode, jeres side, jeres brugeres browsere.

Løsningen · escape

Escape HTML-tegn, før I gemmer

&→&amp;altid først
<→&lt;starter et tag
>→&gt;slutter et tag
"→&quot;i attributter
'→&#039;i attributter
function escapeHtml(text) {
  return text
    .replaceAll("&", "&amp;")
    .replaceAll("<", "&lt;")
    .replaceAll(">", "&gt;")
    .replaceAll('"', "&quot;")
    .replaceAll("'", "&#039;");
}

& først, ellers escaper I jeres egne entities igen. Browseren viser &lt; som tegnet <, men læser det ikke som et tag.

Løsningen · før og efter

Samme angreb, gemt to forskellige måder

Uden escapeHtml() 
"text": "<img src=x onerror=\"alert('hacked')\">"
Browseren viser⚠ hacked
→
Med escapeHtml() 
"text": "&lt;img src=x onerror=&quot;alert(&#039;hacked&#039;)&quot;&gt;"
Browseren viser<img src=x onerror="alert('hacked')">
I POST /messages: escape både spørgsmål og svar 
const message = { type: "question", text: escapeHtml(question), createdAt: ... };
const answerMessage = { type: "answer", text: escapeHtml(result.answer), createdAt: ... };

escapeHtml() beskytter kun det, der gemmes fra nu af. Ryd gamle beskeder med DELETE /messages.
