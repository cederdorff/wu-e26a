02 Problemet

Hvad sker der,
når koden vokser?

Jo mere kode i ét sted — én fil, én funktion — jo sværere er det at finde rundt i, genbruge og teste isoleret.

Kort demo

Routes, logik og data — blandet sammen i én fil

// server.js — alt i én fil
async function loadStudents() { /* fs.readFile(...) */ }
async function saveStudents(students) { /* fs.writeFile(...) */ }

app.get("/students", async (request, response) => {

Routing, forretningslogik og data-adgang er tre forskellige slags arbejde — hver bør leve sit eget sted, så de kan ændres og testes uafhængigt af hinanden. Ikke et nyt princip — I kender det allerede, bare under andre navne.

03 Modules

Import
& Export

Løsningens første skridt — og faktisk noget I allerede har gjort, hver gang I skrev import express from "express". Det er præcis det, der gør det muligt at dele koden op i flere moduler, i stedet for én stor fil.

Det nye: jeres egne filer

export gør jeres egen kode tilgængelig for andre filer

Samme import/export-syntaks, I allerede bruger med import express from "express" — men nu er det jeres egen funktion, ikke en pakke fra npm. Uden det ville al kode skulle bo i samme fil.

// data-helpers.js
export async function loadStudents() {
  const data = await fs.readFile(
    "./data/students.json", "utf8"
  );
  return JSON.parse(data);
}
// server.js
import { loadStudents } from "./data-helpers.js";

app.get("/students", async (request, response) => {
  const students = await loadStudents();
  response.json(students);
});

Navnene i { } skal matche præcis det, den anden fil eksporterer — og stien skal starte med ./ og ende på .js. Det er præcis loadStudents()/saveStudents(), I flytter til sit eget modul om lidt.

To slags export

Named eller default — hvornår bruger man hvad

Samme fil, samme funktion — men to måder at eksportere den på, med forskellig konsekvens ved import.

Named export 
// data-helpers.js
export function loadStudents() { /* ... */ }
export function saveStudents(students) { /* ... */ }
// server.js
import { loadStudents, saveStudents } from "./data-helpers.js";

Flere eksports fra samme fil — navnet i { } skal matche præcis det, filen eksporterer.

Default export 
// data-helpers.js
export default function loadStudents() { /* ... */ }
// server.js
import hentStuderende from "./data-helpers.js";

Kun én pr. fil, ingen { } — og I må selv navngive den ved import.

Tommelfingerregel: named, når filen har flere ting at tilbyde (som vores data-modul) — default, når den kun har én.

Begreb

DRY — Don't Repeat Yourself

Den samme logik bør kun stå ét sted. Det er netop derfor, vi skriver funktioner — loadStudents() og saveStudents() findes, så fs.readFile()/JSON.parse() ikke skal skrives forfra i hver eneste route.

Uden funktion — gentaget i hver route 
router.get("/", async (request, response) => {
  const data = await fs.readFile(
    "./data/students.json", "utf8"
  );
  const students = JSON.parse(data);
  response.json(students);
});
router.post("/", async (request, response) => {
  const data = await fs.readFile(
    "./data/students.json", "utf8"
  );
  const students = JSON.parse(data);
  students.push(request.body);
  // ...
});
→
Med funktion — kaldes blot 
router.get("/", async (request, response) => {
  const students = await loadStudents();
  response.json(students);
});
router.post("/", async (request, response) => {
  const students = await loadStudents();
  students.push(request.body);
  await saveStudents(students);
  // ...
});

Gælder også på tværs af ressourcer — loadTeachers() bliver næsten identisk med loadStudents(). Samme kode to steder er tegn på en manglende funktion.

04 Express Router

En selvstændig
"mini-app"

Én router pr. ressource, monteret på hoved-appen — uden at kende sin egen fulde sti.

Begreb

En Router er jeres helt egen mini-app, for én ressource

Hvad er det?

Et objekt fra express.Router() — det kan præcis det samme som app: .get(), .post(), .put(), .delete(), og kan bruge middleware.

Hvad bruger vi det til?

At samle alle ruter for én ressource i sin egen fil — routes/students.js kender kun til students, intet andet.

Routeren eksporteres, ligesom modulerne i sidste kapitel — server.js importerer den blot.

express.Router()

Routeren kender ikke sit eget mount-punkt

I routes-filen

router.get("/", ...) og router.get("/:id", ...) — routeren definerer kun stier relativt til sig selv.

I server.js

app.use("/students", studentsRouter) sætter den fulde sti først, når routeren monteres — Express lægger /students foran alt, routeren selv definerer.

router.get("/") monteret på /students bliver til GET /students — router.get("/:id") bliver til GET /students/:id.

Mønsteret

Fra routes i server.js til en monteret Router

Før 
app.get("/students", async (request, response) => {
  const students = await loadStudents();
  response.json(students);
});
→
Efter 
// routes/students.js
router.get("/", async (request, response) => {
  const students = await loadStudents();
  response.json(students);
});

Selve logikken er uændret — kun stien ("/students" → "/") og hvor koden bor.

Montér routeren

server.js bliver til opsætning og montering

import express from "express";
import studentsRouter from "./routes/students.js";
import teachersRouter from "./routes/teachers.js";

const app = express();
app.use(express.json());

app.use("/students", studentsRouter);
app.use("/teachers", teachersRouter);

app.listen(3000);

Ingen route-definitioner tilbage i server.js — kun import og montering af to routere.

Før / efter Router-split

Ti routes i én fil bliver til to filer, én pr. ressource

Før:                          Efter:

server.js                     server.js
 ├─ loadStudents()/            ├─ app.use("/students",
 │   saveStudents()            │   studentsRouter)
 ├─ loadTeachers()/            └─ app.use("/teachers",
 │   saveTeachers()                teachersRouter)
 ├─ 5 routes for /students
 └─ 5 routes for /teachers    routes/students.js
                                └─ loadStudents()/saveStudents()
                                   + 5 routes

                               routes/teachers.js
                                └─ loadTeachers()/saveTeachers()
                                   + 5 routes

Rør ikke: selve CRUD-logikken — kun placeringen ændrer sig

Test efter hver fil: hele CRUD-flowet, før I går videre

Bemærk: loadX()/saveX() bor stadig i routes-filen her

Vejen igennem koden

Sådan finder et request vej efter Router-splittet

Request→server.js→routes/students.js→data/students.json

server.js monterer routeren — routes/students.js taler stadig direkte med JSON-filen, det flytter næste kapitel.

Begreb

Single Responsibility — saml det, der ændrer sig sammen

Ikke "gør kun én ting" bogstaveligt — et ansvar er netop det: en grund til at ændre sig. Det, I lige har lavet med Router-splittet, er et konkret eksempel.

routes/students.js

Ændrer sig kun, når students-logikken gør — nye felter, nye regler, nye routes for netop denne ressource.

routes/teachers.js

Rører I slet ikke, når I retter i students — de to filer har hver deres egen, uafhængige grund til at ændre sig.

Derfor virker Router-splittet: hver fil har nu kun ét ansvar — én ressource.

05 Lagdelt arkitektur

Data-modul
& controllers

En route håndterer HTTP ind/ud — ikke filsystemet. Data-adgangen flytter videre til sit eget modul.

Samme princip, ny led

Single Responsibility gælder også på tværs af lag

Sidst splittede I pr. ressource. Nu splitter I langs en anden led — pr. slags arbejde.

routes/students.js

  • Ændrer sig kun, når HTTP-håndteringen gør

data/students.js

  • Ændrer sig kun, når datalageret gør — JSON-fil i dag, database senere

Samme grundregel begge steder: saml det, der ændrer sig sammen, adskil det, der ikke gør.

Begreb

Encapsulation — skjul hvordan, vis kun hvad

En funktion, en router eller et modul bør have en simpel udadvendt facade — og gemme detaljerne for sig selv. Kalderen skal vide, hvad den kan bruges til, ikke hvordan den virker indeni. Det går igen flere steder i dag.

Funktioner · fra Modules

loadStudents()Skjuler fs.readFile() + JSON.parse() bag et navn

Express Router

app.use("/students", studentsRouter)Skjuler, hvordan routeren håndterer GET/POST/PUT/DELETE internt

Data-modulet · om lidt

data/students.jsSkjuler om data ligger i en JSON-fil eller en database

Skift databagvedliggeren senere, og kun data/students.js skal ændres — ikke routes-filen.

Frivilligt · begreb

Controller — endnu et ansvar, endnu et lag

Hvad er det?

En funktion, der stadig tager (request, response) ligesom en route — men indeholder forretningslogikken for én handling: hente, filtrere, validere, gemme, og selv svare klienten.

Hvornår?

Ingen fast grænse — start i routen, og flyt logikken ud den dag flere trin og regler gør routen besværlig at læse.

Samme regel som ved Router-splittet: Single Responsibility — routen matcher kun sti til funktion, controlleren afgør hvad der skal ske.

Frivilligt · eksempel

Routen kalder controlleren, som gør arbejdet

routes/students.js 
import { createStudent } from
  "../controllers/studentsController.js";

router.post("/", createStudent);
→
controllers/studentsController.js 
export async function createStudent(
  request, response
) {
  const students = await loadStudents();
  const newStudent = {
    id: Date.now(),
    name: request.body.name,
    education: request.body.education
  };

  students.push(newStudent);
  await saveStudents(students);
  response.json(newStudent);
}

Routen bliver til en ren "sti → funktion"-mapning — al logikken, inklusiv request/response, flytter med ind i controlleren.

Frivilligt · mappestruktur

Ét lag mere: controllers ved siden af routes og data

students-rest-api/
├── controllers/
│   └── studentsController.js   (getAllStudents, createStudent...)
├── data/

Routen: hvilken route matcher stien? — intet andet

Controlleren: hent, filtrér, sortér, paginér, find/opdatér, gem

Data-modulet: rører controlleren kun via loadX()/saveX()

I dag: I skal ikke nå at bygge controllers — kun vide, hvornår det giver mening

06 request.query

Filtrering, sortering
& paginering

Klienten bestemmer selv, hvilken del af listen den får — via query parameters i URL'en.

Udforsk request.query

Alt efter ? i URL'en havner i ét objekt

router.get("/", async (request, response) => {
  console.log(request.query);

  const students = await loadStudents();
  response.json(students);
});
GET /students
→ {}

GET /students?education=Datamatiker
→ { education: "Datamatiker" }

GET /students?page=2&limit=5
→ { page: "2", limit: "5" }

Alle værdier er strings, uanset hvad de "ligner" — page skal igennem Number(), før det regnes med.

Tre query-baserede værktøjer

Hver query parameter løses med sin egen array-metode

Kilde: freeCodeCamp — REST API Best Practices ↗
filter()?education=...behold kun de elementer, hvor betingelsen er sand
sort()?sort=...sortér efter en property, angivet i query'en
slice()?page=&limit=udsnit af listen — beregnet ud fra side og sidestørrelse

Rækkefølgen betyder noget: filtrér og sortér før I paginerer — ellers pagineres der i den forkerte liste.

Sat sammen

Filtrering → sortering → paginering, i den rækkefølge

router.get("/", async (request, response) => {
  let students = await loadStudents();
  if (request.query.education) {
    students = students.filter((s) => s.education === request.query.education);
  }
  if (request.query.sort) {
    const key = request.query.sort;
    students = students.sort((a, b) => (a[key] > b[key] ? 1 : -1));
  }
  if (request.query.page && request.query.limit) {
    const page = Number(request.query.page);
    const limit = Number(request.query.limit);
    const start = (page - 1) * limit;
    students = students.slice(start, start + limit);
  }
  response.json(students);
});

Ingen query parameters sat? Så returneres hele listen, uændret — hvert trin er en if, ikke et krav.
