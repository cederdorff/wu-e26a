02 SSR og CSR

Hvor bliver
HTML'en bygget?

Samme mål — data skal vises i browseren — men to forskellige steder at gøre arbejdet.

Introducér de to modeller, før EJS bliver konkret. Pointen er ikke at CSR er forkert, men at vi i dag bevidst vælger SSR. [Sources] - Lokal lektionsside: undervisning/008-race-2-ejs-templating-form-handling-og-svar-logik-03-09-2026.md [/Sources]
Definition · SSR vs. CSR

Serveren eller browseren — hvem bygger HTML'en?

SSR · Server-Side Rendering

Serveren kombinerer data og en template og sender færdig HTML til browseren. Express gør det med response.render(), og EJS genererer HTML'en.

CSR · Client-Side Rendering

Serveren sender typisk data — ofte JSON. JavaScript i browseren bygger eller opdaterer selv brugerfladen.

I dagens løsning bruger vi SSR: browseren modtager allerede-færdig HTML.

Knyt gerne til deres Firebase-erfaring fra kurset: der byggede browserens JavaScript ofte HTML'en selv ud fra JSON — det er CSR. I dag flytter vi den opgave over til serveren. [Sources] - Lokal lektionsside: undervisning/008-race-2-ejs-templating-form-handling-og-svar-logik-03-09-2026.md [/Sources]
I dag · SSR i praksis

Browseren beder om en side — serveren afleverer den færdig

BrowserSender requestGET / eller POST /submit
Requestmetode + URL + body
ServerExpress + EJSresponse.render() bygger HTML
Responsestatus + HTML
BrowserViser sideningen ekstra JavaScript krævet

Al logikken kører på serveren — browseren modtager kun det færdige resultat.

Denne illustration gør SSR-definitionen konkret, før EJS' egne tags introduceres. Peg på, at browserens eneste opgave her er at vise den HTML, den modtager — ingen fetch, intet JavaScript, der bygger DOM'en om. [Sources] - Lokal øvelse: opgaver/express-ejs-formular.md [/Sources]
03 EJS

Embedded
JavaScript

En template engine, der lader os skrive HTML med JavaScript-logik indeni.

EJS står for Embedded JavaScript. Det er stadig HTML, men med to slags specialtags. [Sources] - Lokal lektionsside: undervisning/008-race-2-ejs-templating-form-handling-og-svar-logik-03-09-2026.md [/Sources]
EJS' to grundtags

Logik uden output — og escaped output

<% %>

Kører JavaScript-logik uden selv at skrive noget til HTML'en. Bruges til if, for og variable.

<%= %>

Skriver en værdi ind i HTML'en og escaper den — brugerens input bliver til tekst, ikke til HTML.

Escaping betyder, at fx <strong>Ada</strong> vises med vinklerne i stedet for at browseren gør teksten fed. Brug altid <%= %> til data fra brugeren. [Sources] - Lokal øvelse: opgaver/express-ejs-formular.md [/Sources]
Fra route til HTML

response.render() finder templaten og sender data med

app.set("view engine", "ejs");

app.post("/submit", (request, response) => {
  const name = request.body.name;

  response.render("index", { name });
});
<!-- views/index.ejs -->
<% if (name) { %>
  <p>Hej, <%= name %>! 👋</p>
<% } %>

{ name } gør variablen name tilgængelig i index.ejs.

Peg på sammenhængen: samme navn (name) bruges i request.body, i objektet der sendes til render, og i EJS-templaten. Det er den røde tråd, øvelse 1 bygger op omkring. [Sources] - Lokal øvelse: opgaver/express-ejs-formular.md [/Sources]

Definition · Middleware

Middleware er kode, der kører på vejen mellem request og route

Hvad? Funktioner, Express kører før eller mellem jeres routes. Hvorfor? Fælles opgaver — som at læse en formular eller servere en fil — løses ét sted og genbruges af alle routes.

request→express.urlencoded()→express.static()→route handler→response 
app.use(express.urlencoded({ extended: true }));
app.use(express.static("public"));

Rækkefølgen betyder noget: middleware skal stå før de routes, der har brug for den.

Dette formaliserer begrebet, før det bruges konkret i cyklus-diagrammet på næste slide. express.urlencoded() gør request.body tilgængeligt; express.static() gør filer i public/ hentbare uden en dedikeret route. Begge er eksempler på middleware — kode der kører før jeres egne routes. [Sources] - Lokal øvelse: opgaver/express-ejs-formular.md - opgaver/express-ejs-amabot.md [/Sources]

05 Validering og svarlogik

Serveren stoler
ikke blindt på input

Tomt eller ugyldigt input skal give en forståelig fejl — ikke et crash.

Overgang til øvelse 2. Browserens required er nyttig, men serveren skal selv kontrollere data. [Sources] - Lokal øvelse: opgaver/express-ejs-formhaandtering-svarlogik.md [/Sources]
Tre forskellige opgaver

Validering, sanitering og escaping løser ikke det samme

Validering

Afgør, om input må bruges — fx om et navn eller en alder mangler eller er ugyldig.

Sanitering

Ændrer input, fx ved at fjerne uønskede kontroltegn, før det gemmes eller vises.

EJS-escaping

Gør en værdi sikker at skrive i HTML med <%= %> — uden at ændre selve dataen.

Hold de tre begreber adskilt: de løser forskellige problemer.

Denne skelnen er central i både øvelse 2 og AMAbot-øvelsen. Advar mod at forsøge et hjemmelavet “XSS-filter” ved at fjerne ord som script — brug i stedet EJS' escaped output. [Sources] - Lokal øvelse: opgaver/express-ejs-amabot.md [/Sources]
If/else-kæden

Kontrollér én regel ad gangen — render altid til sidst

let error = "";

if (!name || name.trim() === "") {
  error = "Skriv dit navn, før du sender formularen.";
} else if (!age || Number.isNaN(Number(age))) {
  error = "Skriv en alder som et tal.";
} else {
  names.push(name);
}

response.render("index", { name, age, error, names });

Kun ét kald til response.render() — uanset om der var en fejl eller ej.

Dette er den samlede POST-route fra øvelse 2. Peg på rækkefølgen: start uden fejl, kontrollér én regel ad gangen, og render til sidst med de aktuelle data. Samme mønster genbruges direkte i AMAbot-øvelsen. [Sources] - Lokal øvelse: opgaver/express-ejs-formhaandtering-svarlogik.md [/Sources]
